# Архитектура сайта по жизненному циклу ОКС

## 1. Статус и источники

Документ содержит исходную архитектуру этапа 1 и последующие решения по реализации. Актуальное решение по навигации — **раздел 17: единая иерархическая карта**. Оно заменяет прежние решения об отдельных внутренних страницах, постоянной информационной панели и её кнопке перехода, а также более ранние описания мобильной сетки. Типы и репозиторий реализованы; исторические разделы сохранены для прослеживаемости решений. Следующие этапы требуют подтверждения пользователя.

Источники требований:

1. [ТЗ версии 1.0](../ТЗ_сметное_дело.md).
2. Уточнения и архитектурные решения, согласованные с пользователем в диалоге.
3. [Правила статусов и 21 проверочный сценарий](content-status-rules.md).
4. [Карта миграции](content-migration.md), основанная на существующих исходниках.

Запрошенный путь `docs/ТЗ_сметное_дело.md` отсутствует. Использован существующий файл в корне; он не перемещается и не копируется. Старая инструкция `CODEX_INSTRUCTION_smetchik_site.md` описывает десять этапов и не переопределяет новое ТЗ. При расхождениях приоритет имеют явные уточнения пользователя и новое ТЗ. Правила статусов не меняются этим документом; изменения этих правил впоследствии необходимо согласованно отражать в обоих документах.

Сохраняются React + TypeScript + Vite, CSS, архитектурно-техническая эстетика, HashRouter и текущая схема GitHub Pages. Полное переписывание приложения не требуется.

## 2. Общая структура

Главная страница содержит шесть процессов. Номер и последовательность задаются данными, а не фиксированной геометрией компонентов.

| № | Процесс | Блоки / направления |
| --- | --- | --- |
| 01 | Предпроектная стадия | Расчёт смет по укрупнённым показателям (НЦС); расчёт с применением объектов-аналогов |
| 02 | Инженерные изыскания и проектные работы | Расчёт смет на проведение инженерных изысканий; расчёт смет на проектные работы |
| 03 | Проектная стадия (архитектурно-строительное проектирование) | П; Р; исполнительная смета; проверка достоверности определения сметной стоимости |
| 04 | Стадия строительства | НМЦК; смета контракта; учёт выполненных работ |
| 05 | Эксплуатация, ремонт и реконструкция | Комплект проектно-сметной документации для капитального ремонта; комплект сметной документации для текущего ремонта; сметы на техническую эксплуатацию и техническое обслуживание |
| 06 | Снос | Восемь операций непосредственно под процессом; искусственный промежуточный блок не создаётся |

Процесс 05 имеет рабочее название из ТЗ. Реконструкция, монтаж и наладка в будущем добавляются как самостоятельные блоки через данные. Пока для них не создаются ни карточки, ни операции, ни предполагаемое содержание. Число процессов, блоков и операций не ограничивается шестью или текущим числом блоков в UI, типах либо CSS.

### 2.1. Процессы 01 и 02

Четыре направления являются самостоятельными блоками. Каждый поддерживает описание, исходные данные, порядок расчёта и документы. НЦС не смешивается с аналогами; изыскания не смешиваются с проектными работами. Конкретный состав документов пока не определён. Наличие структурного блока не является основанием для создания предполагаемых образцов, шаблонов или инструкций.

### 2.2. Процесс 03

П и Р — независимые блоки с независимыми операциями и каталогами.

| П: разработка проектной документации | Р: разработка рабочей документации |
| --- | --- |
| Сбор и анализ исходных данных | Сбор и анализ исходных данных |
| Ведомость объёмов работ (ВОР) | Ведомость объёмов работ (ВОР) |
| Локальный сметный расчёт | Локальная смета |
| Конъюнктурный анализ цен | Конъюнктурный анализ цен |
| Объектный сметный расчёт | Объектная смета |
| Сводный сметный расчёт | Сводный сметный расчёт |
| Сводка затрат | Сводка затрат |
| Пояснительная записка | Пояснительная записка |

Совпадающие названия не означают совпадение ID, документов или файлов. Автоматическое объединение либо копирование материалов между П и Р запрещено.

Блок «Исполнительная смета» самостоятельный; состав материалов уточняется. Полное название четвёртого блока: «Проверка достоверности определения сметной стоимости строительства, реконструкции и капитального ремонта ОКС (экспертиза)». Его конкретный состав также уточняется. Перечни предполагаемых требований, замечаний и исходных данных не превращаются в вымышленные документы.

### 2.3. Процесс 04

Для НМЦК создаётся структура без неподтверждённого перечня документов.

В блоке «Смета контракта» три операции:

1. Ведомость конструктивных элементов.
2. Проект сметы контракта.
3. Смета контракта.

В блоке «Учёт выполненных работ» непосредственно размещаются документные позиции, без обязательной операции-обёртки:

1. Акты выполненных работ — форма КС-2.
2. Справка о стоимости выполненных работ и затрат — форма КС-3.
3. Журнал учёта выполненных работ — форма КС-6а.
4. Ведомость о расходе основных материалов в строительстве — форма М-29.
5. Накладная на отпуск материалов на сторону — форма М-15.

Состав позиций определён ТЗ; файлы, назначения и описания добавляются только при наличии подтверждённого содержания. Отсутствие файлов не скрывает существование определённых позиций.

## 3. Иерархия и модель сущностей

```text
Общая структура
└── Process
    ├── DocumentPosition выбранного региона → Material[]
    ├── Operation → DocumentPosition[] → Material[]
    └── Block
        ├── DocumentPosition[] → Material[]
        └── Operation → DocumentPosition[] → Material[]
```

Документы допускаются непосредственно у процесса, блока или операции. Дочерние структурные элементы и прямые документы могут сосуществовать. Обязательные пустые промежуточные уровни запрещены.

| Сущность | Поля и назначение |
| --- | --- |
| Process | `id`, `order`, `title`, необязательные `shortDescription`, `description`, `iconKey`, `abbreviations`, `keywords` |
| Block | Общие структурные поля и обязательный `processId` |
| Operation | Общие структурные поля и `parent`: ссылка на процесс или блок |
| NodeRef | Размеченная ссылка `{ kind: 'process' / 'block' / 'operation', id }` |
| Region | Стабильный `id`, название и ключ темы; на первой версии `moscow` и `regions` |
| RegionalNodeContent | `regionId`, `owner: NodeRef`, `definition: 'not-defined' / 'defined'`; ровно одна запись для каждой пары регион + узел |
| DocumentPosition | `id`, `regionId`, `owner: NodeRef`, `order`, `title`; необязательные `documentTypeId`, `description`, `abbreviations`, `tags`, `updatedAt`, `responsible` |
| Material | `id`, `documentId`, `order`, `title`, `typeId`; необязательные `description`, `url`, `format`; регион наследуется от документа |
| MaterialType | `id`, `title`, необязательный `iconKey`; расширяемый справочник |
| DocumentType | Расширяемый справочник типов документных позиций; наполняется только подтверждёнными значениями |

ID стабильны, уникальны в коллекции; составной ключ ссылки включает тип сущности. ID региональных документов и материалов должны также однозначно различаться между каталогами. Номер и название не используются как идентичность. У каждого вложенного элемента один владелец. Процесс и блок документа вычисляются по родительской цепочке, без дублирующих независимых полей. Процесс — корень, поэтому родителя не имеет.

Документная позиция — именованная единица каталога. Материал — конкретный связанный ресурс. Одна позиция может иметь несколько материалов; один материал принадлежит одной позиции. Тематические перекрёстные ссылки не меняют владельца. В случае подтверждённого использования одного файла в нескольких каталогах включение задаётся явно; автоматическое объединение по URL или названию запрещено.

Общие подтверждённые описания, исходные данные и последовательности действий хранятся как содержание структурного узла. Региональные пояснения хранятся в соответствующем региональном слое. Отсутствующие тексты и реквизиты не генерируются из предположений.

### 3.1. Типы материалов

Начальный справочник поддерживает образец, шаблон, инструкцию, нормативный документ, папку Google Drive и дополнительные справочные материалы. Наличие типа в справочнике не создаёт материал автоматически.

Тип материала — открытый строковый ID, проверяемый по справочнику, а не закрытый union, требующий изменения JSX при расширении. Компонент берёт подпись из данных. Если специальная иконка не задана, используется общая; неизвестный `typeId` является ошибкой данных. Добавление типа и материала не требует отдельного React-компонента.

## 4. Региональные каталоги

Процессы, блоки и операции общие. Записи наполнения, документы, ссылки и региональные пояснения самостоятельны для Москвы и регионов.

```text
src/data/lifecycle/{processes,blocks,operations}.ts
src/data/catalogs/{regions,materialTypes,documentTypes}.ts
src/data/regions/moscow/{nodeContent,documents,materials}.ts
src/data/regions/regions/{nodeContent,documents,materials}.ts
```

Это будущая организация файлов. Каталог региона регистрируется в источнике данных. Новый регион добавляется через справочник и данные, без создания новой страницы или ветки условий в каждой карточке.

Запросы документов и материалов всегда содержат регион. Отсутствие документов не запускает поиск в другом каталоге. Общие нормативные материалы включаются в каждый каталог явно, а не через неявный fallback.

При переключении региона сохраняется структурный маршрут. Если открыт документ, переход выполняется к его структурному владельцу с новым регионом; аналог по названию не подставляется. Тема переключается через существующий механизм `data-region`. Устаревшие ответы запросов игнорируются; материалы прежнего региона под новым заголовком не показываются.

## 5. Статусы наполнения

Полная спецификация и 21 сценарий закреплены в [content-status-rules.md](content-status-rules.md). Расчёт выполняется для прямого каталога конкретной пары «узел + регион» после проверки целостности.

- `D`: число непосредственных документных позиций.
- `T`: число зарегистрированных материалов этих позиций, включая материалы без ссылки.
- `A`: число материалов с допустимой ссылкой, без подтверждённой отметки о её неработоспособности.
- `U`: число документных позиций без единого зарегистрированного материала.

| Условие | Результат |
| --- | --- |
| Обязательная региональная запись отсутствует, дублируется или некорректна | Ошибка структуры, статус не назначается |
| `not-defined`, `D > 0` | Противоречие данных, статус не вычисляется |
| `not-defined`, `D = 0` | Состав документов и материалов ещё не определён |
| `defined`, `D = 0` | Документы непосредственно на этом уровне не размещены |
| `defined`, `D > 0`, `A = 0` | Документы определены, файлы пока не загружены или ссылки недоступны |
| `defined`, `D > 0`, `A > 0`, `A < T` или `U > 0` | Частичное наполнение: доступно A из T; дополнительно указать U при U > 0 |
| `defined`, `D > 0`, `T > 0`, `A = T`, `U = 0` | Прямой каталог полностью наполнен |

Все счётчики и итоговое состояние вычисляются автоматически. Позиция без материалов не создаёт фиктивную единицу в `T`. Случай «2 из 2 материалов, но ещё одна позиция без материалов» остаётся частичным и сопровождается пояснением.

Прямые статусы не включают потомков. Отдельная сводка подписывается «Во вложенных разделах». Полнота прямого каталога не означает полноту всего поддерева. Наличие документов в дочернем блоке не противоречит `not-defined` прямого каталога процесса.

Пустая ссылка, `#`, запрещённая схема, некорректный URL и адрес-заглушка не дают доступности и действия «Открыть». Проверка синтаксиса не гарантирует существование файла и права Google Drive. Подтверждённо неработающая ссылка исключается из `A`; сведения о проверке должны поступать в общий расчёт. Без проверки нельзя утверждать, что доступ к файлу подтверждён. Технические состояния загрузки и ошибки запроса не являются статусами наполнения.

## 6. ContentRepository и будущая БД

```text
React UI → хуки → ContentRepository → LocalContentRepository → локальные данные
                                  └→ будущая реализация API/БД
```

Будущие модули: `src/types/{lifecycle,document,catalog}.ts`, `src/services/{contentRepository,localContentRepository,searchService}.ts`, `src/utils/{contentSelectors,contentValidation,contentAvailability,contentRoutes,legacyRoutes,searchIndex}.ts`, хуки получения содержания узла и документа.

Контракт репозитория должен поддерживать:

| Группа запросов | Назначение |
| --- | --- |
| `getRegions`, `getStructure` | Настроенные регионы и общее дерево |
| `getNode`, `getAncestors`, `getChildren` | Узел, родительская цепочка и непосредственные дочерние элементы |
| `getNodeContent(owner, regionId)` | Обязательная региональная запись, прямые документы и сведения для статуса |
| `getDocuments(owner, regionId)` | Документы владельца выбранного региона |
| `getDocument(documentId, regionId)` | Документ с проверкой региональной принадлежности |
| `getMaterials(documentId, regionId)` | Материалы только разрешённого документа и региона |
| `getSearchEntries(regionId)` | Данные общего и регионального поисковых индексов |

Это спецификация обязанностей; точные TypeScript-сигнатуры закрепляются на этапе типов и репозитория. Все источники доступны асинхронно. Отсутствующий узел, корректный пустой каталог, отсутствующая обязательная запись и ошибка загрузки различаются в контракте. Нельзя маскировать ошибку структуры через `?? []`.

UI не импортирует массивы каталогов напрямую. Расчёт статусов и селекторы общие для страниц, карточек и поиска. Запросы учитывают отмену либо защиту от устаревшего результата.

Подготовка к БД означает стабильные ключи, нормализованные связи, сериализуемые данные без React-элементов и функций, границу репозитория и независимость UI от хранения. На первой версии не реализуются БД, административная панель, авторизация, история изменений или фильтры по ответственным и периодам. Поля и запросы допускают такое расширение позже.

## 7. Поиск, маршруты и публикация

Верхние разделы `/schema`, `/documents`, `/regulations` сохраняются. Нормативная база — представление подтверждённого регионального контента, а не независимый дублирующий источник файлов.

Примеры будущих hash-маршрутов (ID иллюстрируют формат, не являются созданными записями):

```text
#/schema?region=moscow
#/schema/processes/:processId?region=moscow
#/schema/processes/:processId/blocks/:blockId?region=moscow
#/schema/processes/:processId/operations/:operationId?region=moscow
#/schema/processes/:processId/blocks/:blockId/operations/:operationId?region=moscow
#/documents/:documentId?region=moscow
```

URL — источник текущего выбора. Генераторы ссылок централизованы; вложенные адреса проверяют родительскую цепочку. Breadcrumbs ведут к владельцам и карте, сохраняя регион. Поддерживаются прямое открытие, обновление страницы, Back/Forward, неверные адреса, фокус и прокрутка к найденному элементу.

Старые параметры `stage`, `item`, `mode` обрабатывает адаптер. Однозначное соответствие перенаправляется с `replace`; неоднозначное предлагает выбор, неизвестное показывает объяснение и карту. Старые десять этапов не сохраняются как параллельная пользовательская схема. Подробности — в карте миграции.

Поисковый индекс включает процессы, блоки, операции, документные позиции и материалы выбранного региона. Учитываются названия, подтверждённые описания, сокращения, ключевые слова и тематические обозначения. Существующая нормализация русского текста сохраняется. Результат содержит тип, процесс, контекст блока/операции, регион, описание при наличии и прямой адрес. Общая структура доступна в обоих режимах; документы другого региона не выдаются.

Результат материала открывает его документную позицию внутри сайта с выделением материала; внешний ресурс открывается явным действием в новой вкладке с `noopener noreferrer`. Карточки доступных файлов дают прямое действие открытия; несколько материалов отображаются отдельными действиями, а не произвольным выбором первой ссылки. Будущие фильтры задаются параметрами запроса, а не условными ветвями каждого компонента.

Сохраняются `HashRouter`, production `base: '/smeta-map/'` и `.github/workflows/deploy.yml`. Пути ресурсов строятся через импорты и при необходимости `import.meta.env.BASE_URL`. Вложенные hash-адреса не требуют серверных rewrite. Изменение workflow, Git-настроек и публикация не входят в этап 1.

## 8. Обязательные правила разработки и целостности

1. П и Р не объединяются; документы и материалы не копируются между ними автоматически.
2. Региональные каталоги не смешиваются; отсутствие данных одного региона не компенсируется другим.
3. Фиктивные документы, URL, реквизиты, сроки, ответственные и пояснения запрещены. Тестовые данные не попадают в пользовательский каталог.
4. Новый процесс, блок, операция, документ, материал и тип материала добавляются преимущественно данными, без персонального React-компонента.
5. Процесс 05 расширяется данными; будущие направления не наполняются предположениями.
6. Проверяются уникальность ID, обязательные поля, допустимые типы родителей, существование владельцев и документов, известность регионов и справочных типов, порядок соседних элементов и однозначность пути. Циклы и осиротевшие ссылки запрещены.
7. Для каждой пары регион + структурный узел обязательна ровно одна корректная запись наполнения. Переход на новый регион требует таких записей для всей общей структуры.
8. Проверяются запрет `not-defined` с прямыми документами, региональная принадлежность и отсутствие открытия без допустимой ссылки; счётчики не вводятся вручную.
9. Повтор одного URL не объединяет документы автоматически; семантика материалов требует подтверждения.
10. Существующие файлы не удаляются и не перемещаются без отдельного разрешения. Устаревшие модели впоследствии можно исключить из активных импортов, сохраняя файлы.

## 10. Реализация модели и проверок: этап 2

По отдельному поручению пользователя этап 2 включает также чистый расчёт статусов, первоначально запланированный для этапа каталогов. Реальные каталоги, шесть процессов, репозиторий, хуки и интерфейс ещё не создаются и не подключаются.

Созданы `src/types/lifecycle.ts`, `src/types/document.ts`, `src/types/catalog.ts` и независимые утилиты `contentValidation.ts`, `contentAvailability.ts`, `materialLinks.ts`. Старые `Region`, `Stage`, `ProcessItem` и `resourceRepository` не изменены: они обслуживают прежний UI до его миграции. Новый `RegionDefinition` описывает открытый справочник, включая исходные ID `moscow` и `regions`, без ограничения будущих территорий.

`validateContentSnapshot(unknown)` проверяет целостный снимок и возвращает `valid` и список `issues` с `severity`, `code`, `path`, `elementId` при наличии ID и русским сообщением. Ошибка структуры блокирует расчёт и открытие; недопустимый строковый URL возвращается предупреждением `invalid-url`, а материал считается недоступным. Это позволяет корректно вычислить согласованное состояние «файлы отсутствуют / ссылки недоступны», а не подменять его ошибкой структуры. Нестроковый URL и отметка `working` без допустимого URL — ошибки данных.

`getContentAvailability` возвращает либо ошибку без статуса, либо вычисленные статус, счётчики и сообщение. Значения: `not-defined`, `no-direct-documents`, `unavailable`, `partial`, `complete`. Исходный `definition` не заменяется производным статусом. Проверяется весь снимок; при ошибках в другом каталоге он также не признаётся целостным. Расчёт остаётся прямым, без суммирования потомков.

`Material.linkCheck` допускает `unchecked`, `working`, `broken`. Отсутствие отметки не подтверждает удалённый доступ; `broken` исключает материал из доступных. `getRegionalMaterialHref` проверяет снимок, регион и принадлежность документа, затем возвращает допустимый адрес либо `null`. Низкоуровневый `getMaterialHref` проверяет только адрес и отметку, поэтому для будущего пользовательского действия применяется региональная функция. Google Drive API и сетевые проверки не выполняются.

Проверки находятся в `tests/content-model.test.ts`; синтетические данные не импортируются приложением. Запуск без новых зависимостей на Node.js 24: `node --test tests/content-model.test.ts`. Отдельная строгая проверка тестов и новых модулей: `npx.cmd --no-install tsc --ignoreConfig --noEmit --strict --target es2023 --module nodenext --moduleResolution nodenext --allowImportingTsExtensions --types node tests/content-model.test.ts`. В Windows используются `.cmd`, чтобы не менять PowerShell ExecutionPolicy. Проверки приложения: `npx.cmd --no-install tsc -b --pretty false`, `npm.cmd run lint`, `npm.cmd run build`.

Покрыты правила статусов и целостности сценариев 1–14, 16–20. Ошибочный вход не даёт ложного статуса отсутствия файлов. Полные сценарии 15 (поздний ответ при переключении региона) и 21 (загрузка/ошибка асинхронного запроса) остаются проверками этапа 5: в чистых функциях этапа 2 нет запросов и состояния загрузки. Внутри П и Р созданы по восемь операций. Каждая позиция имеет собственный региональный ID; П и Р независимы даже при совпадении названия.

В блоке сметы контракта созданы три операции и три соответствующие именованные документные позиции. Пять форм учёта работ расположены непосредственно в блоке `work-accounting`, без операций-обёрток. В капитальном ремонте созданы пять именованных позиций, в текущем — три, в сносе — пять.

Сбор и анализ исходных данных, расчёт смет на работы по обследованию и конъюнктурный анализ цен представлены операциями. Конкретные перечни документов, отчётов и файлов для этих действий не заданы и не изобретаются. Это не означает отсутствия операции: её название и порядок полностью сохранены из ТЗ.

Поэтому фиктивные записи материалов без подтверждённого состава не создаются. Когда конкретный материал будет определён до получения файла, модель позволяет добавить его без `url`; сейчас отсутствие файлов выражается документными позициями без материалов.

## 12. Реализация ContentRepository и хуков

По следующему отдельному поручению пользователя реализован слой доступа к существующим данным. Структура, каталоги, типы сущностей, валидатор и расчёт наполнения не создавались заново и не изменялись. Новый слой не подключён к прежним компонентам, маршрутам и поиску.

### 12.1. Модули и выбор источника

- `src/services/contentRepository.ts` — интерфейс ContentRepository, типы результатов, ошибок и представлений узла/документа.
- `src/services/localContentRepository.ts` — LocalContentRepository. Принимает существующий ContentSnapshot либо функцию его получения, в том числе асинхронную. Не импортирует исходные каталоги и не зависит от React.
- `src/services/contentRepositoryInstance.ts` — точка композиции: существующий `lifecycleContent` передаётся локальному репозиторию, экземпляр экспортируется через интерфейс ContentRepository.
- `src/services/contentRequest.ts` — контроллер загрузки, повторного запроса, отмены и подавления устаревших результатов. Не зависит от React и физического источника.
- `src/hooks/useContentQuery.ts`, `useNodeContent.ts`, `useDocument.ts` — React-адаптеры с возможностью передачи другой реализации репозитория.

Для подключения API создаётся реализация того же интерфейса и меняется точка композиции. Контракт не содержит импортов локальных массивов, транспорта API или JSX. Полноценный поиск и `getSearchEntries` пока не реализованы.

### 12.2. Методы

Все методы асинхронны и принимают необязательные `ContentRequestOptions` с AbortSignal. Кроме получения списка регионов, каждый метод требует явный `regionId`, включая запрос общей структуры.

| Метод | Результат при успехе |
| --- | --- |
| `getRegions(options?)` | Справочник настроенных регионов |

### 12.3. Результаты, ошибки и изоляция

`ContentResult<T>` — размеченное объединение:

- `success` с `data`, включая корректный пустой список;
- `not-found` с сообщением для отсутствующего узла или документа в выбранном регионе;
- `error` с кодом, сообщением и, при ошибках структуры, исходной диагностикой валидатора.

Коды ошибок: `unknown-region`, `missing-catalog`, `invalid-data`, `source-error`, `aborted`. Отсутствующий каталог или обязательная запись не превращаются в успешный пустой результат. Документ другого региона возвращает not-found, без раскрытия его данных и без fallback.

Каждый запрос проверяет весь исходный снимок существующим валидатором. Поэтому ошибка целостности другого каталога также препятствует успешному чтению; это продолжает строгое правило этапа 2. Недопустимый строковый URL остаётся предупреждением, а не блокирующей ошибкой; существующий расчёт исключает такой материал из доступных.

После проверки создаётся структурная копия. Изменение выданного объекта не меняет исходные массивы и другой регион. Между запросами нет скрытого постоянного кэша: повтор читает источник заново, в том числе после ошибки. Источник не обязан поддерживать отмену: обёртка завершает ожидание при abort и снимает обработчик события при завершении.

### 12.4. Хуки и жизненный цикл запроса

Общий `useContentQuery(query, repository?)` поддерживает четыре вида запроса: structure, node, document, catalog. Тип данных определяется видом запроса. Два коротких адаптера — `useNodeContent(owner, regionId, repository?)` и `useDocument(documentId, regionId, repository?)`. Для процесса в useNodeContent передаётся `{ kind: 'process', id: processId }`; аналогично для блока и операции. Дополнительные хуки для каждого списка не создаются.

Результат хука содержит `status`, `loading`, `reload()` и поля соответствующего состояния. Состояния: loading без прежних данных, success с данными, not-found с сообщением, error с типизированной ошибкой. Состояния загрузки не подменяют статусы наполнения внутри NodeContent.

Механизм построен на useSyncExternalStore, useMemo и useEffect:

1. Ключ запроса включает вид, регион и идентификатор/NodeRef. Смена ключа или реализации репозитория создаёт отдельный контроллер уже при render. Первый снимок — loading без data, поэтому московские документы не показываются под новым регионом до запуска эффекта.
2. Эффект запускает запрос; очистка вызывает cancel, увеличивающий поколение запроса и прерывающий AbortController.
3. reload отменяет прежний запрос и немедленно убирает прежние data, публикуя loading. После завершения проверяются поколение и signal.
4. Поздний успех или ошибка отменённого запроса игнорируются, даже если источник не поддерживает AbortSignal.
5. При размонтировании отписка и cancel исключают поздние публикации. Повторный setup после cleanup в React StrictMode поддерживается.

### 13.1. Активный интерфейс

Процессы и блоки могут иметь собственные прямые документы одновременно с дочерними разделами.

Документ открывается отдельной страницей с материалами. MaterialList использует типы из репозитория, а не закрытый список в JSX. Функциональная раскладка вынесена в styles/lifecycle.css. Сохранены основная оболочка, header, footer, существующие переменные, региональные темы, SVG и SchemaHero (с обновлённой подписью). Окончательный дизайн карты, новые анимации и поиск не реализуются на этом этапе.

### 13.2. Маршруты

HashRouter и production base не изменяются. Внутренние адреса:

```text
#/schema?region=moscow
#/schema/processes/:processId?region=moscow
#/schema/processes/:processId/blocks/:blockId?region=moscow
#/schema/processes/:processId/operations/:operationId?region=moscow

```

К каждому адресу узла допускается суффикс `/documents/:documentId`. Это канонический адрес документа с явным контекстом владельца. Короткий адрес `#/documents/:documentId?region=...` также поддерживается и после успешного чтения заменяется каноническим через Navigate replace. Каталоги остаются по `/documents` и `/regulations`.

contentRoutes.ts централизует построение путей, определение NodeRef и проверку полной родительской цепочки. Возврат ведёт на известный родительский путь, поэтому работает при прямом открытии без предшествующей истории. AppLayout переводит фокус к main и прокручивает страницу при изменении адреса; skip-link не меняет hash-маршрут.

При старых `stage`/`item` главная показывает объяснение изменения структуры и новую карту. Полный адаптер предметных соответствий старых URL пока не реализован: старые ID не используются для произвольного выбора П/Р или регионального документа.

### 13.3. Регион и состояния

Структурный адрес при смене региона сохраняется. Вложенный адрес документа переводится к его владельцу и загружает прямой каталог нового региона. Короткий адрес документа без известного контекста переводится в каталог документов. Документ другого региона по прямому адресу показывает not-found; подстановка по похожему названию запрещена.

## 14. Интерактивная горизонтальная карта (этап 6)

### 14.1. Данные и управление

LifecycleHomePage по-прежнему запрашивает общую структуру через useContentQuery и ContentRepository. Добавлен LifecycleMap: он получает структуру, регион и выбранный ID через props. Отдельного массива процессов, новых полей модели или специальных наборов данных для карты нет.

По последнему уточнению пользователя при непустой структуре всегда выбран процесс: при отсутствии выбранного ID или его устаревании используется первый процесс в порядке данных. Стрелки выбирают соседние процессы с переходом через край, Home/End — первый/последний, Escape возвращает фокус к активной карточке, не скрывая сведения. utils/lifecycleMap.ts содержит чистые функции: компактная подпись из исходного названия (без изменения данных), сводка состава и клавиатурный индекс. Сводка считает непосредственные блоки и все операции процесса: как прямые, так и принадлежащие его блокам. Для сноса корректно показываются 0 блоков и 8 операций. В информационной области отображаются полное название, имеющиеся описания, реальные названия блоков либо прямых операций и вычисленные количества. Новые описания не сочиняются.

### 14.2. Desktop

При ширине от 1366 px все процессы находятся в одной CSS Grid-строке в порядке данных. Выбранная колонка получает вес 3.2, остальные пять — по 0.85, то есть активная примерно в 3.76 раза шире каждой вторичной. Шаблон хранится в CSS-переменной --lifecycle-columns; React не задаёт inline grid-template-columns, поэтому адаптивные правила управляют раскладкой без !important. Переход grid-template-columns, ширины и высоты кнопок плавный. Выбранная карточка графитовая, с полным названием и количеством блоков/операций; вторичные показывают краткую производную подпись без описаний.

Карточки соединяет тонкая линия с направляющими стрелками. Минимальный общий SVG-маркер встроен в код; дополнительные библиотеки и растровые изображения не требуются. Палитра и координатная сетка наследуются от существующей региональной темы.

Высота страницы не ограничивается; вертикальная прокрутка для чтения содержимого допустима. У главной страницы отключены min-height: 100svh оболочки и flex-grow основного содержимого: футер следует за содержимым, а не растягивает пустую область. ### 14.3. Узкие экраны и доступность

По последнему уточнению пользователя горизонтальная лента полностью заменена сеткой. На ширине 768–1365 px используются три колонки и два ряда, включая проверки 768, 991 и 1024 px. До 767 px используется одна колонка и шесть строк — последняя явно указанная пользователем мобильная схема 1 × 6 заменяет прежние две колонки. Все шесть процессов постоянно присутствуют в навигационной композиции; внутренней прокрутки между ними нет.

Удалены scrollTo, scroll-snap, обработчики прокрутки, свайпов и колеса, ResizeObserver и связанные таймеры. На планшетах и телефонах карточки центрируются внутри равных ячеек CSS Grid. Активная занимает всю ширину своей ячейки и увеличивается по высоте, остальные немного сужаются. Масштабирование поверх соседних ячеек не применяется: размеры меняются в нормальном потоке, поэтому сетка отводит место всем карточкам. Направляющие стрелки показываются только между соседями одного ряда.

На телефонах область сведений находится ниже всей сетки, ссылка открытия занимает доступную ширину; иллюстрация остаётся компактной рядом с заголовком. Для названий используются переносы строк, без line-clamp и ограничения максимальной высоты. Горизонтальное переполнение контейнера запрещено через overflow-x: clip; сами ячейки используют minmax(0, 1fr), элементы имеют min-width: 0. Это защитное ограничение, а не способ спрятать дополнительные процессы: ни одна карточка не размещается вне ширины сетки. Вертикальная прокрутка страницы допускается для чтения всего содержимого, внутренней прокрутки между процессами нет.

prefers-reduced-motion отключает переходы и анимацию появления сведений. Полное название каждой карточки доступно через aria-label и title даже при компактной видимой подписи. Для объявления выбора используется отдельный live region; состав доступен обычной семантической разметкой. Выбор и отдельный переход «Открыть процесс», клавиатурное управление и сохранение региона остаются прежними.

Операции под процессом и документы на любом из трёх структурных уровней поддерживаются существующими связями. Обязательные промежуточные уровни не вводятся. ### 17.2. Раскрытие и компоненты

- LifecycleHomePage получает структуру через useContentQuery и хранит выбор процесса в query-параметре `process`. Отсутствие выбора означает свёрнутую карту. Повторный выбор активного процесса и Escape сворачивают его. Другой процесс заменяет раскрытую структуру; история браузера восстанавливает выбор процесса.
- LifecycleMap сохраняет все шесть карточек. Вместо кнопки «Открыть процесс» и статического перечня состава выводится LifecycleTree. На desktop дерево под общей строкой; на телефоне и планшете LifecycleProcessRows вставляет единственную панель после законченной выбранной строки.
- LifecycleTree использует существующий useNodeContent. LifecycleTreeContent отображает только непосредственных детей и прямые documentSummaries текущего узла. Ветви блока и операции имеют собственное состояние раскрытия; открытие или закрытие соседней ветви его не меняет. Сворачивание родителя размонтирует потомков и сбрасывает их локальное раскрытие.
- Документная ветвь показывает название, тип из справочника (либо явное «Тип документа не указан»), вычисленный статус, общее и доступное количество материалов. Раскрытая ветвь получает DocumentContent через существующий useDocument и отображает общий MaterialList. Справочники типов не зашиты в JSX. У каждого материала собственные название, тип, формат при наличии, описание и допустимый URL.
- Данные загружаются по раскрытию, а не копируются из исходных массивов в UI. Ошибки, отсутствие результата и загрузка отображаются через QueryFeedback с повторной загрузкой.

Без прямых документов не добавляется пустая карточка «Документы этого уровня» рядом с существующими потомками. `not-defined` явно сообщает о неопределённом составе. Определённый конечный узел без документов сообщает, что на этом уровне они не размещены. Статусы и счётчики берутся из репозитория; потомки не превращаются в прямые документы родителя.

### 17.3. Региональная изоляция и асинхронность

Регион передаётся в каждый запрос узла и документа. При переключении региона дерево размонтируется по ключу региона; hooks создают новый контроллер запроса без старого результата. Имеющиеся AbortController, номер поколения запроса и cleanup защищают от позднего ответа и публикации после размонтирования. Структурный выбор процесса, блока и операции из прямой ссылки может сохраняться; региональные `document` и `material` удаляются из query при смене региона. Новый документ другого каталога не подбирается автоматически и не раскрывается вместо прежнего.

Отсутствующий каталог остаётся явной ошибкой. Запрос чужого ID документа не вызывает fallback. Локальное состояние раскрытия старого дерева не переносит материалы между регионами. Переход на API или базу данных не требует изменения компонентов дерева: транспорт остаётся за асинхронным контрактом ContentRepository.

### 17.4. Материалы: только Яндекс Диск

materialLinks.ts является общим правилом доступности для MaterialList, валидации и вычисляемых счётчиков. Разрешены HTTPS-ссылки с точным hostname `disk.yandex.ru` или `yadi.sk`, непустым путём, без credentials и нестандартного порта. Чужие сервисы, поддомены-двойники, относительные адреса, некорректное кодирование и `linkCheck: broken` не дают действия открытия и не учитываются как доступные материалы. Примерные Google Drive URL прежних тестов заменены тестовыми адресами Яндекс Диска; запрещённые адреса остались в негативных сценариях. Производственные ссылки не создавались.

Внешние ссылки открываются в новой вкладке с `rel="noopener noreferrer"`. Отсутствующий/недопустимый URL сопровождается сообщением о недоступности. Допустимость URL не подтверждает существование удалённого файла или права доступа: сетевой проверки, OAuth, API и синхронизации на этом этапе нет. Правила явно подтверждённой рабочей/нерабочей ссылки сохраняются.

### 17.5. Анализ маршрутов и совместимость прежних адресов

До изменения AppRoutes проверены входы в LifecycleNodePage, LifecycleDocumentPage и LifecycleCatalogPage, ссылки Header, RegionSwitch и навигация AppLayout. HashRouter и настройки Vite, GitHub Pages и GitHub Actions сохранены. Новые отдельные страницы уровней не создаются.

Прежние пути `/schema/processes/:processId[/blocks/:blockId][/operations/:operationId]` и их документные варианты обслуживает LegacyMapEntry. Он получает узел или документ из выбранного каталога через useContentQuery, проверяет родительскую цепочку с matchesContentRoute и перенаправляет с replace на `/schema?region=…&process=…&block=…&operation=…&document=…` (только имеющиеся уровни). Короткий `/documents/:documentId` также определяет родителей по репозиторию. Чужой документ, неизвестный узел и неверная цепочка дают явное сообщение, без подбора похожего содержимого.

Параметры `block`, `operation` и `document` — начальное раскрытие ветви, например при старой прямой ссылке. Последующие независимые раскрытия локальны; история браузера гарантирует выбор процесса, а не каждое открытие ветви. `/documents` и `/regulations` возвращают на единую карту: прежние отдельные списки более не используются. В Header оставлен вход «Схема» и переключение региона. Исходники прежних страниц и их компонентов сохранены, хотя AppRoutes больше их не импортирует. Исторические nodePath/documentPath остаются для совместимости сохранённых компонентов и тестов.

AppLayout сбрасывает прокрутку и фокус при смене пути или региона, но не при выборе процесса на той же карте: query-изменение выбора не уводит пользователя наверх. Это изменение не добавляет горизонтальной прокрутки.

### 17.6. Адаптивность и доступность

Телефон до 767 px — две колонки, три строки для текущих шести процессов; 768–1365 px — три колонки; от 1366 px — одна строка с увеличением активной колонки и пропорциональным сжатием остальных. Независимо от раскладки карточки остаются в контейнере. В сетках отображаются полные длинные названия с переносами; на desktop активная карточка показывает полное название, остальные — компактную производную подпись. Доступное название каждой кнопки всегда полное.

Иерархия обозначена тонкими направляющими, отступами, иконками и подписями уровней; открытая ветвь выделяется акцентной рамкой. На телефоне отступы уменьшены, кнопки не ниже 44 px, длинные названия и адреса переносятся. Палитра и координатный фон сохраняются. Грубые соединительные выступы не возвращаются. Раскрытие использует существующую короткую анимацию; prefers-reduced-motion отключает её. aria-expanded, связи aria-controls и нативные кнопки обеспечивают управление с клавиатуры. Используется семантика вложенных списков, без неполной имитации ARIA treeview.

### 17.7. Проверки и ограничения приёмки

Node/SSR-набор дополнен tests/lifecycle-tree.test.ts: все процессы, непосредственные потомки, самостоятельность П/Р, прямые операции сноса, документы на каждом уровне без смешивания с потомками, региональная изоляция, неопределённый состав и ограничения Яндекс Диска. Обновлены тесты карты и MaterialList: выбранная панель, начальное свёрнутое состояние, отсутствие переходов на отдельные страницы, несколько материалов, форматы, описания, новые типы и отсутствие открытия без допустимой ссылки. Размещение панели после правильной строки автоматически проверяется для всех шести выборов в группах по два и три. Существующие проверки запросов покрывают поздние ответы, ошибки и отмену при размонтировании.

Браузерная dev-страница tests/browser/index.html обновлена под новую концепцию: независимое раскрытие ветвей, сворачивание процесса, документы всех уровней, несколько материалов, регион и поздний ответ, прямые старые ссылки, ошибки и история браузера. Геометрические iframe-сценарии подготовлены для 375, 390, 768, 1024, 1366 и 1440 px, включая все шесть выборов, положение дерева после строки, переполнение, области нажатия и reduced-motion при включённой системной настройке.

Фактический запуск браузера в текущей сессии заблокирован недоступностью browser access host («The browser access host is unavailable»). Поэтому интерактивные браузерные сценарии, реальные замеры адаптивности и визуальная оценка не считаются выполненными. Результаты TypeScript, lint, Node/SSR и production-сборки приводятся в отчёте отдельно от подготовленных браузерных сценариев. Следующие этапы и публикация не выполняются.

Итоговая автоматическая проверка текущего решения: 85 Node/SSR-тестов проходят; строгий TypeScript для тестов и browser harness, TypeScript приложения, lint и production-сборка проходят. Vite HMR отключён в SSR-тестовых серверах, чтобы параллельные тесты не конкурировали за websocket-порт. Браузерные проверки остаются невыполненными по указанной выше причине.
