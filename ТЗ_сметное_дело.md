# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## Разработка образовательного информационно-справочного сайта «Ценообразование и сметное дело на жизненном цикле объектов капитального строительства»

**Версия:** 1.0\
**Статус:** техническое задание на разработку\
**Тип продукта:** адаптивный образовательный информационно-справочный
веб-сайт.

------------------------------------------------------------------------

## 1. Общая концепция проекта

### 1.1. Назначение сайта

Разработать информационно-справочный сайт, предназначенный для
систематизации и представления материалов по ценообразованию и сметному
делу на всех основных стадиях жизненного цикла объектов капитального
строительства (ОКС).

Сайт должен объединять: - структурированную карту сметных процессов; -
справочную информацию по отдельным направлениям сметной деятельности; -
перечни документов и материалов; - ссылки на образцы, шаблоны и
нормативную документацию; - навигацию по материалам, размещённым на
Google Drive.

Основной принцип построения --- последовательное раскрытие информации от
общего жизненного цикла объекта к конкретным сметным операциям и
документам.

### 1.2. Целевая аудитория

Сайт предназначен для участников образовательного процесса: - студентов
строительных и экономических направлений; - преподавателей; - слушателей
образовательных программ по сметному делу; - специалистов, изучающих
ценообразование в строительстве.

Интерфейс должен быть понятен пользователям с разным уровнем
профессиональной подготовки.

### 1.3. Основная задача

Обеспечить пользователю возможность быстро определить, на какой стадии
жизненного цикла объекта он находится, какие сметные работы выполняются
на этой стадии, какие документы формируются и где найти необходимые
материалы.

------------------------------------------------------------------------

## 2. Принципиальные архитектурные решения

При разработке необходимо соблюдать следующие решения:

1.  Полностью отказаться от прежней схемы, состоящей из десяти этапов.
2.  В основу главной страницы положить жизненный цикл объекта
    капитального строительства.
3.  Выделить шесть крупных процессов.
4.  Для каждого процесса предусмотреть собственную внутреннюю структуру.
5.  Реализовать раздельные версии материалов для Москвы и регионов.
6.  Использовать вложенную навигацию: процесс → внутренний блок →
    операции и документы.
7.  Предусмотреть возможность расширения структуры без изменения общей
    архитектуры сайта.

Москва и регионы должны иметь одинаковую логическую структуру, но
собственные наборы документов и ссылок.

------------------------------------------------------------------------

## 3. Общая структура сайта

### 3.1. Главная страница

Главная страница представляет собой интерактивную карту жизненного цикла
объекта капитального строительства.

На ней необходимо разместить шесть основных процессов:

1.  Предпроектная стадия.
2.  Инженерные изыскания и проектные работы.
3.  Проектная стадия (архитектурно-строительное проектирование).
4.  Стадия строительства.
5.  Эксплуатация, ремонт и реконструкция.
6.  Снос.

Каждый процесс отображается в виде отдельной интерактивной карточки.

В карточке необходимо предусмотреть: - порядковый номер; - название
процесса; - небольшую тематическую иконку; - короткую поясняющую
подпись; - визуальный индикатор возможности перехода внутрь.

При нажатии на карточку пользователь переходит к внутреннему содержанию
соответствующего процесса.

### 3.2. Внутренняя структура процесса

Внутри каждого процесса отображаются предусмотренные для него
направления сметной деятельности.

Каждое направление может включать: - описание выполняемых работ; -
последовательность действий; - перечень необходимых исходных данных; -
сметные расчёты; - документы; - нормативные материалы; - образцы и
шаблоны; - ссылки на Google Drive.

Необходимо предусмотреть возможность перехода на следующий уровень
вложенности без перегрузки интерфейса.

### 3.3. Логика навигации

Основной сценарий:

**Главная страница → Процесс → Направление / блок → Операции и документы
→ Открытие материала.**

Пользователь должен иметь возможность: - вернуться к предыдущему
уровню; - перейти на главную карту; - переключить регион; -
воспользоваться поиском; - открыть документ непосредственно из
соответствующего блока.

Предусмотреть отображение навигационной цепочки (breadcrumbs), чтобы
пользователь понимал своё положение в структуре сайта.

## 4. Содержание и структура основных процессов

### ПРОЦЕСС 01. Предпроектная стадия

Внутри процесса необходимо разместить два самостоятельных направления в
виде активных кнопок или карточек.

#### Направление 1. Расчёт смет по укрупнённым показателям (НЦС)

При переходе открывается отдельный раздел, содержащий: - описание
направления; - исходные данные; - порядок расчёта; - ключевые
документы; - образцы и дополнительные материалы.

#### Направление 2. Расчёт с применением объектов-аналогов

При переходе открывается отдельный раздел, содержащий: - описание
метода; - необходимые исходные данные; - порядок применения
объектов-аналогов; - ключевые документы; - образцы и дополнительные
материалы.

Документы для НЦС и объектов-аналогов должны размещаться раздельно.
Объединять их в общий перечень не следует.

Состав конкретных документов будет определён при наполнении сайта.

### ПРОЦЕСС 02. Инженерные изыскания и проектные работы

Внутри процесса предусмотреть две самостоятельные активные кнопки.

#### Направление 1. Расчёт смет на проведение инженерных изысканий

Содержит отдельный перечень документов и материалов, относящихся к
определению стоимости инженерных изысканий.

#### Направление 2. Расчёт смет на проектные работы

Содержит отдельный перечень документов и материалов, относящихся к
определению стоимости проектных работ.

Для каждого направления предусмотреть: - описание; - исходные данные; -
последовательность расчёта; - ключевые документы; - образцы и шаблоны.

Документы двух направлений не должны смешиваться.

### ПРОЦЕСС 03. Проектная стадия (архитектурно-строительное проектирование)

Внутри процесса предусмотреть четыре крупных блока.

#### Блок 3.1. Стадия «П» --- разработка проектной документации

Внутри блока разместить следующие элементы:

1.  Сбор и анализ исходных данных.
2.  Ведомость объёмов работ (ВОР).
3.  Локальный сметный расчёт.
4.  Конъюнктурный анализ цен.
5.  Объектный сметный расчёт.
6.  Сводный сметный расчёт.
7.  Сводка затрат.
8.  Пояснительная записка.

Каждый элемент должен открывать соответствующие справочные материалы и
документы.

#### Блок 3.2. Стадия «Р» --- разработка рабочей документации

Предусмотреть аналогичную структуру:

1.  Сбор и анализ исходных данных.
2.  Ведомость объёмов работ (ВОР).
3.  Локальная смета.
4.  Конъюнктурный анализ цен.
5.  Объектная смета.
6.  Сводный сметный расчёт.
7.  Сводка затрат.
8.  Пояснительная записка.

Стадии «П» и «Р» должны быть самостоятельными разделами.

Несмотря на сходство состава, нельзя автоматически объединять их
документы и материалы. Для каждого раздела предусматривается собственный
каталог.

#### Блок 3.3. Исполнительная смета

Создать самостоятельный раздел «Исполнительная смета».

Предусмотреть возможность размещения: - справочной информации; - порядка
формирования исполнительной сметы; - необходимых исходных данных; -
образцов и шаблонов; - связанных документов.

Подробный состав материалов будет определён дополнительно.

#### Блок 3.4. Проверка достоверности определения сметной стоимости

Название раздела:

«Проверка достоверности определения сметной стоимости строительства,
реконструкции и капитального ремонта ОКС (экспертиза)».

Предусмотреть отдельный раздел для материалов, связанных с проверкой
сметной стоимости.

В дальнейшем здесь должны размещаться: - требования к представляемой
документации; - состав материалов; - порядок проверки; - замечания и
корректировки; - образцы и сопутствующие документы.

Конкретный перечень материалов подлежит дополнительному наполнению.

### ПРОЦЕСС 04. Стадия строительства

Внутри процесса необходимо создать три самостоятельных блока.

#### Блок 4.1. Определение начальной максимальной цены контракта (НМЦК)

Создать отдельный раздел, посвящённый определению начальной максимальной
цены контракта.

Предусмотреть возможность размещения: - исходных данных; - методики
определения стоимости; - расчётных материалов; - документов, связанных с
формированием НМЦК.

#### Блок 4.2. Смета контракта

Внутри блока разместить три элемента:

1.  Ведомость конструктивных элементов.
2.  Проект сметы контракта.
3.  Смета контракта.

Каждый элемент должен иметь собственную карточку с возможностью перехода
к документам и материалам.

#### Блок 4.3. Учёт выполненных работ

Внутри блока разместить следующие документы:

1.  Акты выполненных работ --- форма КС-2.
2.  Справка о стоимости выполненных работ и затрат --- форма КС-3.
3.  Журнал учёта выполненных работ --- форма КС-6а.
4.  Ведомость о расходе основных материалов в строительстве --- форма
    М-29.
5.  Накладная на отпуск материалов на сторону --- форма М-15.

Для каждого документа предусмотреть: - название; - назначение; - краткое
описание; - образец или шаблон; - ссылку на соответствующий файл Google
Drive.

### ПРОЦЕСС 05. Эксплуатация, ремонт и реконструкция

Рабочее название раздела. Он объединяет эксплуатацию объекта, текущий
ремонт, реконструкцию, капитальный ремонт, монтаж и наладку.

Внутри процесса предусмотреть три самостоятельных блока.

#### Блок 5.1. Комплект проектно-сметной документации для капитального ремонта

Состав:

1.  Сбор и анализ исходных данных.
2.  Расчёт смет на работы по обследованию.
3.  Дефектная ведомость.
4.  Локальная смета.
5.  Конъюнктурный анализ цен.
6.  Объектная смета.
7.  Сводный сметный расчёт.
8.  Пояснительная записка.

#### Блок 5.2. Комплект сметной документации для текущего ремонта

Состав:

1.  Сбор и анализ исходных данных.
2.  Дефектная ведомость / акт.
3.  Локальная смета.
4.  Конъюнктурный анализ цен.
5.  Пояснительная записка.

#### Блок 5.3. Сметы на техническую эксплуатацию и техническое обслуживание

Создать самостоятельный раздел для материалов по определению стоимости
технической эксплуатации и технического обслуживания объектов.

На текущем этапе предусмотреть структуру раздела без заполнения
неподтверждёнными сведениями.

Состав документов и операций будет добавлен после получения
дополнительных материалов.

### ПРОЦЕСС 06. Снос

Создать самостоятельный раздел, посвящённый сметной документации при
сносе объектов капитального строительства.

Состав раздела:

1.  Сбор и анализ исходных данных.
2.  Расчёт смет на работы по обследованию.
3.  Дефектная ведомость.
4.  Локальная смета.
5.  Конъюнктурный анализ цен.
6.  Объектная смета.
7.  Сводный сметный расчёт.
8.  Пояснительная записка.

Для каждого элемента предусмотреть возможность размещения справочной
информации и соответствующих документов.

## 5. Региональная структура: Москва и регионы

### 5.1. Общий принцип

На сайте должны существовать две самостоятельные версии информационного
наполнения:

-   Москва;
-   Регионы.

Логическая структура процессов, блоков и операций в обеих версиях
идентична.

Различаются: - нормативные документы; - региональные нормативные базы; -
сборники и ценовые источники; - образцы и шаблоны; - дополнительные
справочные материалы; - ссылки на Google Drive.

### 5.2. Переключатель региона

На главной странице предусмотреть заметный переключатель:

**\[ Москва \] \[ Регионы \]**

При смене региона: - сохраняется общая структура сайта; - обновляется
состав документов; - меняются ссылки; - обновляются региональные
справочные материалы; - сохраняется текущий уровень навигации, если
соответствующий раздел существует в обеих версиях.

Если для выбранного направления в другом регионе материалы отсутствуют,
необходимо показывать понятное сообщение об отсутствии наполнения, а не
пустую страницу.

### 5.3. Визуальное различие регионов

Для обеспечения визуальной идентификации регионов допускается
использовать разные акцентные цветовые темы.

Москва --- терракотовые и тёплые оттенки.

Регионы --- оливковые и приглушённые зелёно-серые оттенки.

При этом: - общая стилистика сохраняется; - структура и размеры
элементов не меняются; - различие не должно мешать восприятию
информации.

## 6. Работа с документами и Google Drive

### 6.1. Источник документов

Основным хранилищем материалов на текущем этапе является Google Drive.

Сайт не должен самостоятельно хранить копии всех документов.

В интерфейсе размещаются карточки документов, содержащие ссылки на
соответствующие файлы или папки Google Drive.

### 6.2. Карточка документа

Для каждого документа предусмотреть следующие поля:

-   название;
-   тип документа;
-   краткое описание;
-   принадлежность к процессу;
-   принадлежность к внутреннему блоку;
-   регион;
-   ссылка на Google Drive;
-   формат файла, если известен.

Дополнительно предусмотреть возможность добавления: - даты обновления; -
статуса документа; - ответственного; - тематических меток.

### 6.3. Переход к документу

При нажатии на карточку документа пользователь перенаправляется
непосредственно к соответствующему материалу на Google Drive.

Открытие документов рекомендуется выполнять в новой вкладке браузера.

Необходимо предусмотреть: - корректную обработку отсутствующих ссылок; -
понятное сообщение при отсутствии документа; - визуальное различие между
доступными материалами и ещё не заполненными карточками.

### 6.4. Требования к наполнению

На этапе разработки использовать тестовые данные и временные ссылки.

Не создавать вымышленные документы и не подменять отсутствующие
материалы случайными файлами.

Структура должна позволять впоследствии массово добавлять документы без
изменения компонентов интерфейса.

## 7. Поиск и навигация по материалам

### 7.1. Общий поиск

Реализовать поиск по всему содержимому сайта.

Поиск должен учитывать: - названия процессов; - названия внутренних
блоков; - названия операций; - названия документов; - аббревиатуры; -
тематические обозначения.

Примеры поисковых запросов:

-   НЦС;
-   ВОР;
-   ЛСР;
-   ССРСС;
-   КС-2;
-   М-29;
-   капитальный ремонт;
-   конъюнктурный анализ.

### 7.2. Результаты поиска

В результатах поиска необходимо отображать: - название найденного
элемента; - его тип; - принадлежность к процессу; - регион; - краткое
описание.

При нажатии пользователь должен попадать непосредственно в
соответствующий раздел сайта.

### 7.3. Фильтрация

Архитектуру поиска необходимо подготовить к дальнейшему внедрению
фильтров.

Возможные параметры: - тип документа; - процесс; - регион; -
ответственный; - статус; - период обновления.

Полноценную систему фильтрации не требуется реализовывать до определения
окончательной структуры базы данных.

## 8. Требования к визуальному оформлению и UX/UI

### 8.1. Общая стилистика

Сохранить архитектурно-техническую эстетику существующего проекта.

Основные характеристики: - современный минимализм; - нейтральная
цветовая база; - выразительная типографика; - технические графические
элементы; - умеренное использование анимации; - отсутствие избыточной
декоративности.

Основная палитра: - тёплый серый; - графитовый; - серо-бежевый; -
тёмно-бежевый; - терракотовый; - оливковый.

### 8.2. Главная карта

Главная карта должна визуально отражать последовательность жизненного
цикла объекта.

Карточки шести процессов должны: - иметь единый дизайн; - визуально
различаться по номеру и тематической иконке; - иметь понятное состояние
наведения; - анимироваться при выборе; - обеспечивать переход к
внутреннему содержанию.

На широких экранах допускается расположение шести процессов в одной
горизонтальной линии.

Необходимо избегать чрезмерной пустоты, слишком узких карточек и
перегруженных описаний.

### 8.3. Анимации

Предусмотреть: - плавное увеличение выбранной карточки; - уменьшение или
упрощение вторичных карточек; - плавное раскрытие внутреннего
содержимого; - анимацию переходов между уровнями; - смену цветовой темы
при переключении региона; - мягкую подсветку активных элементов.

Анимации должны быть функциональными и не замедлять работу сайта.

Обязательно поддержать `prefers-reduced-motion`.

### 8.4. Адаптивность

Сайт должен корректно работать на: - настольных компьютерах; -
ноутбуках; - планшетах; - смартфонах.

**Desktop:** - основная карта процессов; - компактные карточки; -
раскрытие подробностей в рабочей области.

**Tablet:** - адаптированное расположение карточек; - сохранение удобной
навигации.

**Mobile:** - вертикальная структура; - раскрывающиеся блоки; - удобные
области нажатия; - отсутствие горизонтальной прокрутки; - центрированная
навигация; - корректное отображение документов.

## 9. Технические требования

### 9.1. Технологическая основа

Сохранить существующую технологическую основу проекта: - React; -
TypeScript; - Vite; - CSS / существующую систему стилей; - GitHub Pages
для размещения.

Не выполнять полную переработку проекта с нуля, если существующая
архитектура позволяет реализовать новую структуру.

### 9.2. Организация данных

Необходимо отделить данные от компонентов интерфейса.

Предусмотреть отдельные наборы данных для Москвы и регионов.

Рекомендуемая логика:

-   `processes` --- основные процессы;
-   `blocks` --- внутренние направления;
-   `operations` --- операции и элементы процесса;
-   `documents` --- документы и материалы;
-   `regions` --- региональные наборы данных.

Каждый элемент должен иметь уникальный идентификатор и связь с
родительским элементом.

Пример логической структуры:

``` text
region
  └── process
       └── block
            └── operation
                 └── documents
```

Необходимо предусмотреть возможность добавления новых элементов через
изменение данных, без необходимости создавать новые React-компоненты для
каждого документа.

### 9.3. Подготовка к базе данных

На первом этапе использовать локальные структурированные данные проекта
(JSON или TypeScript).

При этом доступ к данным необходимо организовать через отдельный слой,
чтобы в дальнейшем можно было подключить полноценную базу данных или API
без полной переработки интерфейса.

### 9.4. Размещение

Сохранить возможность автоматического развёртывания через GitHub Actions
на GitHub Pages.

Обеспечить корректную работу вложенной навигации, ссылок и обновления
страниц при размещении сайта в подкаталоге репозитория.

12. Production-сборка проходит без ошибок.
