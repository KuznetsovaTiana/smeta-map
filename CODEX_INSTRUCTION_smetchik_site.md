# CODEX INSTRUCTION
## Образовательный веб-сервис для сметчиков

### 1. Цель проекта

Необходимо создать отдельный публичный адаптивный веб-сайт для участников образовательного процесса, изучающих сметное дело.

Сайт должен объединять:

- интерактивную карту процесса работы сметчика;
- справочник по этапам и документам;
- навигацию по нормативным и учебным материалам;
- ссылки на документы и папки Google Drive;
- поиск по этапам, документам и понятиям;
- переключение между режимами «Москва» и «Регионы».

Главная идея интерфейса:

> Пользователь сначала видит общий процесс, затем кликает по этапу, проваливается внутрь, выбирает конкретный документ или действие и получает пояснение, связи, материалы и ссылки.

Сайт должен быть удобен на:
- desktop;
- tablet;
- mobile.

На первом этапе backend и полноценная БД не обязательны. Все данные можно хранить в статических TypeScript/JSON-файлах, но архитектура должна позволять позднее заменить их API/БД без переписывания UI.

Основные пользователи:

Главный пользовательский вопрос:

> «На каком этапе проекта я нахожусь, что здесь делает сметчик, какие документы используются и где найти нужный материал?»

# 4. Главная страница

Главная страница строится вокруг интерактивной карты процесса работы сметчика.

На первом уровне показываются только крупные этапы.

Основная последовательность:

1. Предварительная оценка стоимости
2. Исходные данные для сметы
3. Определение объёмов работ
4. Разработка сметной документации
5. Проверка и утверждение стоимости
6. Тендер и договорная стоимость
7. Сметное сопровождение строительства
8. Учёт выполненных объёмов работ
9. Актирование выполненных работ
10. Расчёты и закрытие проекта

Связи между этапами отображаются слева направо.

Не показывать сразу все документы. Использовать progressive disclosure:

- уровень 1 — этапы;
- уровень 2 — внутренние элементы этапа;
- уровень 3 — подробная карточка документа/понятия.

# 6. Москва / Регионы

Реализовать постоянный переключатель:

- Москва
- Регионы

Структура схемы в обоих режимах одинаковая.

Меняются:
- ссылки;
- нормативные материалы;
- примеры;
- шаблоны;
- папки Google Drive;
- региональные документы.

Пример:
пользователь открыл карточку `КС-2`, затем переключился с «Москва» на «Регионы».

Карточка остаётся открытой, но ресурсы и нормативные ссылки обновляются.

Состояние региона должно сохраняться в URL.

Пример:

`/schema?region=moscow&item=ks-2`

# 7. Структура этапов

## 7.1. Этап 1 — Предварительная оценка стоимости

Содержимое:
- Концепция и параметры объекта
- НЦС
- Объекты-аналоги
- Укрупнённые показатели
- Предварительный бюджет проекта

Цель:
показать, как оценивается стоимость до разработки детальной сметной документации.

---

## 7.2. Этап 2 — Исходные данные для сметы

Содержимое:
- ПД / РД
- Чертежи
- Спецификации
- Ведомости
- Технические решения
- Условия строительства

Цель:
показать, откуда сметчик получает исходные данные.

---

## 7.3. Этап 3 — Определение объёмов работ

Содержимое:
- Анализ проектных решений
- Расчёт объёмов
- Проверка единиц измерения
- ВОР

Логика:

`ПД / РД → анализ → расчёт объёмов → ВОР`

---

## 7.4. Этап 4 — Разработка сметной документации

Это главный узел карты.

Показать четыре базовых фактора:

- объём;
- сметная норма;
- стоимость ресурсов;
- условия производства работ.

Визуальная логика:

`Объём + Норма + Цена + Условия = Сметная стоимость`

Содержимое:
- подбор сметных норм;
- стоимость ресурсов;
- коэффициенты;
- учёт условий производства;
- ЛСР / ЛС;
- ОСР / ОС (при необходимости);
- ССРСС.

Связь:

`ВОР + нормы + цены + коэффициенты → ЛСР → ОСР → ССРСС`

Дополнительные ветви:
- оборудование;
- ПНР;
- прочие затраты.

---

## 7.5. Этап 5 — Проверка и утверждение стоимости

Содержимое:
- внутренняя проверка;
- экспертиза (при необходимости);
- замечания;
- корректировка;
- согласование.

Необходимо реализовать обратную связь:

`Проверка → Замечания → Корректировка → Проверка`

---

## 7.6. Этап 6 — Тендер и договорная стоимость

Содержимое:
- закупка / тендер;
- коммерческое предложение;
- согласование стоимости;
- смета к договору;
- договорная цена.

Логика:

`Сметная стоимость → коммерческая / тендерная стоимость → договорная стоимость`

Для бюджетного сценария предусмотреть скрываемую ветвь:
- НМЦК;
- закупочная процедура;
- цена контракта.

На первом этапе фильтр «финансирование» можно не выводить в UI, но структура данных должна позволять добавить его позднее.

---

## 7.7. Этап 7 — Сметное сопровождение строительства

Содержимое:
- изменение РД;
- изменение объёмов;
- дополнительные работы;
- исключаемые работы;
- расчёт изменения стоимости;
- сопоставление «было / стало»;
- корректировка сметы;
- корректировка договорной стоимости;
- дополнительное соглашение при необходимости.

Логика должна быть циклической, а не строго линейной.

Связать с этапами:
- 4;
- 6;
- 8.

---

## 7.8. Этап 8 — Учёт выполненных объёмов

Содержимое:
- фактически выполненные работы;
- подтверждение объёмов;
- накопительный учёт;
- КС-6а (при применении);
- остаток.

Мини-логика:

`Договорный объём - ранее принято - выполнено за период = остаток`

---

## 7.9. Этап 9 — Актирование выполненных работ

Содержимое:
- подтверждённые объёмы;
- договорные расценки;
- акт выполненных работ;
- КС-2 (при применении);
- согласование.

Не использовать «КС-2» как название этапа.

---

## 7.10. Этап 10 — Расчёты и закрытие проекта

Содержимое:
- КС-3 / иной расчётный документ;
- согласование;
- оплата;
- контроль остатка по договору;
- итоговый анализ стоимости.

Итоговые показатели:
- договорная стоимость;
- фактически выполнено;
- принято;
- оплачено;
- остаток;
- экономия / перерасход.

# 10. Смежные документы

Смежные документы не должны отображаться как основные этапы.

Отдельный нейтральный блок:

`Смежные документы`

Подпись:

`Используются в работе сметчика при необходимости, но не являются самостоятельными этапами процесса.`

Содержимое:
- оборудование;
- ПНР;
- прочие затраты;
- М-29;
- М-15;
- АОСР;
- исполнительные схемы;
- журналы работ;
- документы на материалы;
- протоколы испытаний;
- иные подтверждающие документы.

Не создавать ложную последовательность:

`КС-3 → М-29 → М-15`

М-29 и М-15 — отдельный материальный/производственный контур.

Исполнительную документацию связать с этапами 8 и 9 как подтверждение факта и объёма работ.

# 13. Google Drive

На первом этапе документы физически хранятся в Google Drive.

Сайт должен содержать только ссылки.

Не встраивать URL напрямую в компоненты.

Все ссылки хранить в отдельном слое данных.

Пример:

```ts
{
  id: "ks-2",
  title: "КС-2",
  type: "document",
  stageId: "stage-acceptance",

  resources: {
    moscow: [
      {
        id: "ks2-example-msk",
        title: "Пример заполнения",
        type: "example",
        url: "https://drive.google.com/..."
      }
    ],

    regions: [
      {
        id: "ks2-example-region",
        title: "Пример заполнения",
        type: "example",
        url: "https://drive.google.com/..."
      }
    ]
  }
}
```

Сегодня источник:
- Google Drive.

Позднее:
- API;
- БД;
- CMS;
- собственное хранилище.

UI не должен зависеть от конкретного источника.

# 18. Структура данных

## Stage

```ts
interface Stage {
  id: string;

  shortDescription: string;
  description?: string;

  items: string[];

  previous?: string[];
  next?: string[];

```

## ProcessItem

```ts
interface ProcessItem {
  id: string;
  title: string;
  abbreviation?: string;

  type:
    | "document"
    | "method"
    | "calculation"
    | "result"
    | "condition"
    | "regulation"

  shortDescription?: string;
  description?: string;

  inputs?: string[];
  outputs?: string[];

  checklist?: string[];
  commonErrors?: string[];

  tags?: string[];

  resources?: {
    moscow?: Resource[];
    regions?: Resource[];
  };

```

## Resource

```ts
interface Resource {
  id: string;
  title: string;

  type:
    | "template"
    | "example"
    | "regulation"
    | "methodology"
    | "instruction"
    | "video"
    | "folder"
    | "external-link";

  url: string;
  source?: "google-drive" | "external";
  description?: string;
}
```

## Connection

```ts
interface ProcessConnection {
  id: string;

  source: string;
  target: string;

  type:
    | "sequence"
    | "input"
    | "output"
    | "influence"
    | "correction"
    | "related";

  label?: string;
  required?: boolean;
}
```

# 19. Типы линий

`sequence`
- основная последовательность;
- сплошная стрелка.

`input`
- входные данные.

`output`
- результат.

`correction`
- обратная связь / цикл корректировки;
- изогнутая или двусторонняя стрелка.

`influence`
- влияние сквозного фактора;
- тонкая пунктирная линия.

`related`
- смежный документ;
- серый пунктир.

# 25. MVP

Первая рабочая версия должна включать:

1. Публичный сайт.
2. Главную интерактивную схему.
3. 10 этапов.
4. Режим «Обзор».
5. Режим «Подробно».
6. Проваливание внутрь этапа.
7. Карточки документов.
8. Переключатель Москва / Регионы.
9. Глобальный поиск.
10. Ссылки на Google Drive.
11. Sidebar на desktop.
12. Mobile bottom sheet / отдельный экран.
13. Адаптивность.
14. URL-state.
15. Отдельный слой данных без hardcode ссылок в UI.

---

# 26. Не делать в MVP

Не реализовывать без отдельного запроса:
- авторизацию;
- личный кабинет;
- прогресс обучения;
- комментарии;
- избранное;
- собственную БД;
- загрузку файлов пользователями;
- CMS;
- сложную аналитику;
- десятки фильтров.

# 27. UX-сценарии

## Сценарий 1 — Изучение этапа

Пользователь:
1. открывает сайт;
2. выбирает «Москва»;
3. нажимает «Разработка сметной документации»;
4. этап раскрывается;
5. видит ВОР, нормы, цены, ЛСР, ОСР, ССРСС;
6. нажимает ЛСР;
7. справа открывается карточка;
8. нажимает «Открыть пример»;
9. файл открывается в Google Drive в новой вкладке.

---

## Сценарий 2 — Поиск

Пользователь вводит:

`КС-2`

Система:
1. находит элемент;
2. переводит карту к этапу 9;
3. подсвечивает КС-2;
4. открывает карточку;
5. отображает ресурсы для текущего региона.

---

## Сценарий 3 — Прямая ссылка от преподавателя

Преподаватель отправляет:

`/schema?region=moscow&item=vor`

Сайт:
1. открывает режим Москва;
2. переходит к этапу определения объёмов;
3. выделяет ВОР;
4. показывает описание и связанные материалы.

# 28. Критерии готовности

MVP считается готовым, если:

- сайт открывается по публичной ссылке;
- карта корректно отображается на desktop;
- мобильная версия не требует масштабирования браузером;
- можно открыть любой из 10 этапов;
- можно открыть карточку документа;
- Москва / Регионы переключаются без перезагрузки;
- ссылки на Google Drive меняются в зависимости от региона;
- поиск находит этапы и документы;
- URL сохраняет выбранный регион и элемент;
- Back/Forward браузера работают корректно;
- нет hardcoded Google Drive URL внутри React-компонентов;
- новые документы можно добавить через data-файл без изменения UI-компонентов;
- схема не перегружена при первом открытии;
- смежные документы не выдаются за основные этапы.

# 29. Главный принцип реализации

Не строить сайт как набор папок и файлов.

Строить его как интерактивную модель процесса.

Пользователь должен мыслить так:

> «Я нахожусь на определённом этапе проекта → здесь сметчик делает определённые действия → использует конкретные документы → получает конкретный результат → может открыть нужный материал».

Именно эта логика должна определять архитектуру UI, данных, поиска и навигации.
